# 性能优化方案（最终版 · 待审核）

> 更新于 2026-09-14，已并入用户审核意见。

---

## 一句话

现在慢有两个原因：**一是每个号都要白等十几秒**；**二是一个号卡住会把后面的号全堵死**。本方案把这两件事一起解决。

**改完的预期**：单账号从 ~17 秒降到 ~7 秒；最坏阻塞从 **20 分钟**降到 **不到 5 分钟**；再也不会出现"悄无声息地少跑好几个号"。

### ⚠️ 第 8 条的补记（2026-09-15）

**原判断有误。** 第 8 条曾被标为「由第 10 条的两阶段调度实现」，这是偷换了概念：

- 两阶段调度解决的是**登录**排队 —— 所有登录都在第一个抢座之前完成；
- 第 8 条要解决的是**抢座**排队 —— 第 1 个号抢不到时会原地重试到时间用完，
  第 2 个号只能干等，**排在最后的号最多要等 66 分钟才出手**，开抢早已结束。

在 `concurrency: 1`（串行）下，第 8 条**完全没有生效**。

**已按原计划补齐**：`run_all` 的抢座阶段拆成两轮 ——

| 轮次 | 行为 |
| --- | --- |
| 第一轮 | **全部账号各出手一次**（`max_retry=1`），谁都不许多试；抢到的立即通知，不发噪音通知 |
| 第二轮 | **只给第一轮失败的账号补抢**，此时才用完整的「探路 → 猛攻」节奏 |

由新增的 **Test 27** 守住：断言「任何补抢调用都不早于第一轮的最后一个出手」。


**附：新增 DRY RUN 开关**（非原方案条目，为安全验证而加）

- `DRY_RUN=1` → 只走「启动浏览器 → 登录 → 取 UID」即停止，**不发起预约、不发送通知**
- 已接入两阶段调度（DRY RUN 下**不进入抢座阶段**，不发通知）与 `appoint_zwulib(dry_run=True)`
- GitHub 手动触发新增 `dry_run` 勾选项，云端也能安全试
- 覆盖测试：Test 20（不发通知 + 诚实报告）、Test 21（**绝不触发抢座调用**）

> ⚠️ 期间发现并修掉一个测试设计缺陷：两个测试脚本原先**各自复制了一份主循环逻辑**，改 `demo.py` 后测试依然会通过（假绿）。现已改为调用真实调度函数（`demo.run_all`），只替换 `open_session` 这一处接缝。

## 优化清单（共 10 条）

### 第一类：先修坏的地方（不提速，但比提速重要）

#### 1. 一个号崩了不要连累别人

**现在**：每个号的第一步是"开浏览器"，这一步可能失败（浏览器升级、驱动版本对不上、内存不够）。一旦失败，程序**当场报错退出**，排队在后面所有号**一个都不执行，而且一条通知都没有** —— 你会以为它们只是没抢到。

**改成**：给每个号单独包一层保护，出错只影响它自己：

| | 现在 | 改后 |
| --- | --- | --- |
| 第 3 个号出错 | 程序退出，4~10 号全不跑 | 记录后跳过，4~10 号照常跑 |
| 第 3 个号的通知 | **没有**（静默） | 失败通知，说明原因 |
| 4~10 号的通知 | **没有**（静默） | 各自的正常通知 |

**通知格式不变**，仍然是逐条串行发送，顺序不变：

```
预约失败 | 2023xxxx

- 用户: 2023xxxx
- 状态: ❌ 预约失败
- 原因: 浏览器启动失败
```

**附带做一件事：把报错翻译成人话**。异常原文通常是长串英文，直接进微信很难看：

| 原始报错 | 通知里显示 |
| --- | --- |
| WebDriver / Chrome 相关 | 浏览器启动失败 |
| TimeoutException | 登录超时，未成功进入系统 |
| 其他 | 执行异常（详细原因见运行日志） |

完整报错仍打在运行日志里，便于排查。

**改动位置**：`demo.py:453`（主循环加异常捕获）、`zwulib.py:246`（把 `SeatAutoBooker(...)` 构造移入 `try`）。
**验证**：`test_config_layering.py` 已有 mock 注入机制，新增「第 2 个账号抛异常，第 3 个仍被执行」的断言即可离线覆盖。

#### 2. 修一下驱动更新工具的小毛病

`update_driver.py` 要往 `drivers/` 目录写文件，但这个目录不在仓库里，第一次用会报错。改动：写之前先 `os.makedirs(drivers_dir, exist_ok=True)`。

#### 3. 三处"默认房间号"统一

现在 `demo.py:19`、`booking_config.yml:6` 写的是 114，`zwulib.py:239` 的函数默认值写的是 212。漏填一处就会静默约到 212。统一成同一个值。

> ⚠️ 这是**行为变更**，需确认没有其他脚本依赖 `appoint_zwulib()` 的旧默认值。

### 第二类：让它别白等

#### 4. 分阶段耗时埋点（必须最先做）

**现在**：跑完只告诉你成功失败，完全不知道时间花在哪。
**改成**：打印每个环节的真实耗时：

```
[timer] user=2023xxxx 启动=2.31s 登录=1.84s 取UID=0.42s 抢座=0.71s 收尾=0.55s 合计=5.83s
[timer] 全部完成: 8 成功 / 10 个账号，总耗时 61.4s
```

**必须先做**，否则后面第 5、6、10 条的收益无法量化，只能凭感觉。

#### 5. 登录不再死等

**现在**：
- `zwulib.py:190` 打开网页后 `time.sleep(3)` —— **纯冗余**，下一行的 `wait.until` 本来就在等同一个元素
- `zwulib.py:205` 点完登录按钮后 `time.sleep(8)` —— 闭着眼睛等，不管其实 1 秒就登进去了

**改成**：删掉 `sleep(3)`；`sleep(8)` 改成盯着 URL 变化，一登进去立刻往下走（判据复用 `zwulib.py:214` 已有的 `'login' in url` 逻辑，不引入新假设）。

**收益**：每号省 6~7 秒。

> 保留一个 `LOGIN_WAIT_MODE=url|fixed` 开关（默认走新逻辑），万一站点改成不换 URL 的路由方式，可以一键回退、不必改代码。

### 第三类：抢座策略重做（针对"抢指定座位"）

#### 6. 重试节奏改成"前慢后快"

**现在**：每 60 秒试一次，最多 20 次 = 最坏原地卡 **20 分钟**，期间后面的号全部排队干等。

**改成**：

| 阶段 | 节奏 | 次数 | 用途 |
| --- | --- | --- | --- |
| 探路 | 每 **30 秒** 一次 | 最多 8 次 | 程序可能比系统开放时间早启动，先温和地试探 |
| 猛攻 | 每 **3 秒** 一次 | 持续 60 秒 | 系统一开放就全力抢 |
| 结束 | — | — | 总计最坏 ~4 分 40 秒 |

**为什么用「前慢后快」而不是「掐点开抢」**：程序不需要知道"几点开抢"。不管它几点启动、系统几点开放，只要在窗口内就一直在试。这避免了依赖时钟，也避开了图书馆系统开放时刻未必精确到 21:00:00 整的问题。

**收益**：最坏阻塞 1200s → 280s。

#### 7. 候选座位之间不再等 5 秒

`zwulib.py:178` 抢失败一个候选座位要等 5 秒才试下一个，改成 1~2 秒。同一账号连续尝试不同座位号风险很低。

#### 8. 换个顺序：先全员过一轮，再回头补抢

**现在**：第 1 个号抢不到就原地死磕，第 2 个号只能干看着，**错过开抢瞬间**。
**改成**：所有号先各快速出手一轮 → 记下没抢到的 → 全都过完一遍后，再回头给失败的号补抢。

> ⚠️ **这条是第 6 条的前提。** 光把间隔改短没用 —— 第 1 个号照样会先占住那 4 分多钟，后面的号还是进不了场。

### 第四类：小优化

#### 9. 发通知时别重复读 Excel

`notice.py:13-26` 每发一次通知就把整个 `zwu_lib.xlsx` 重新解析一遍（0.3~1 秒），而 `seatmap.py` 里已经有一份进程内缓存。改成复用同一份，同时消除"同一份座位表在两个文件里各写一遍"的维护隐患。

> 依赖方向为 `demo → notice → seatmap → zwulib`，无循环引用，改造安全。

### 第五类：最后做，单独验证

#### 10. B 方案：提前登录，到点只抢

**现在**：每个号是「登录 → 抢」绑在一起串行。慢活（登录约 11 秒）全都落在黄金时间里：

```
号1 登录 ████ 号1抢 号2 登录 ████ 号2抢 号3 登录 ████ 号3抢
```

等最后一个号出手时，座位早没了。

**改成**：把登录全部前置到开抢之前，开抢后只发最轻的 HTTP 请求：

```
开抢前：3 个号依次登录（不计入黄金时间）  |  开抢后：3 个号一起抢（1~2 秒）
```

分三步实现：
1. 把「登录」和「抢座」拆开 —— 所有号先登录完，凭证存内存
2. 抢座阶段不再需要浏览器 → 登录完就 `driver.quit()`，省内存
3. 抢座阶段沿用第 6 条的「前慢后快」节奏，**不需要知道"几点开抢"**

**收益**：3 个号从"约 50 秒才轮到最后一个出手"变成"开抢后 1~2 秒全部出手"。

**唯一的新增风险**：登录与抢座之间从 0 秒拉长到几分钟，**凭证是否仍有效需要实测**。两个保险：

- **小步试**：初期只提前 90 秒，间隔短、风险低；确认没问题再加大
- **自动回退**：抢座时若发现凭证失效，**当场重新登录一次再抢** —— 最坏退回到现在的行为，不会更差

**需要配合的配置改动**：cron-job.org 的触发时间从 `21:00` 提前到 `20:55`（目的是让程序有充裕时间完成登录，不是掐点）。即使 cron 延迟、程序 20:58 才起来，也不影响结果 —— 因为程序不依赖时钟。
